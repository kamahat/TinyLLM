# 03 — Methods compared

The LLM is the hard part. Five approaches were tried, in the order below; each one fixed what the previous one revealed.

## 0. Baseline: a stock small LLM

Qwen3-1.7B (Q4_K_M) with the smart-home framework's prompt and tools, no training. Result on the 92-phrase French benchmark: **17/92 (18 %)** — and only **2/76 on actual commands**: the model writes the tool name in plain text ("HassTurnOn light.living_room") instead of emitting a tool call.

## 1. LoRA fine-tuning

**What:** teach the model the *format* and the *behaviour*: when to call a tool, with which arguments, in French, and when **not** to call one.

| Parameter | Value |
|---|---|
| Base model | `Qwen/Qwen3-1.7B` (bf16) |
| Method | LoRA, rank 32, learning rate 2e-4, gradient accumulation 8, max length 2,000 tokens |
| Loss | **only on the answer tokens** (otherwise long prompts exhaust GPU memory and the model wastes capacity learning the prompt) |
| Hardware | one RTX 5070 (12 GB); ~1 h for the first version, 19 min for a 0.6B model |
| Export | merge → GGUF (f16) → `llama-quantize` **Q4_K_M** (~1.1 GB for 1.7B) → Ollama |
| Data | synthetic, generated by scripts, **no leakage** into the benchmark (same devices, different sentences) |

Iterations:

| Version | Training data | What it fixed |
|---|---|---|
| v1 | 2,124 single-turn examples, full prompt | tool calling: 18 % → 96 % on the first call. But the model **calls the tool again** after the result |
| v2 | 3,844 multi-turn examples: success → "Done", error → refuse and **stop**; zone commands | no loops; clean refusals after a forced error |
| v3 | the prompt the real tablet sends (25 tools) 70 % + 18-tool prompt 30 %; 0–3 turns of history (including the local "Turned on" replies); speech-recognition noise ("lumières" → "vumières"); temperature 0 | the model no longer *imitates* the previous assistant turn |
| v4c | v3 examples converted to the **compact** format | smaller prompt, best model before web search |
| v5 | v4c + web-search instruction + web-search examples (x3) + **synthetic snippets** (3,895 samples) | web search; the model in production |

## 2. RAG: tested, not kept

**Hypothesis:** do not send all devices; retrieve the *k* most relevant ones with an embedding model and send only those.

- Scripts: knowledge pack (one document per device: name, area, synonyms, example phrases), retrieval with `multilingual-e5-base`, retrieval evaluation.
- **Retrieval quality is good**: hit@1 = 94 % on the benchmark.
- But the **end-to-end results are worse**: RAG in the user message gave 26/31 (84 %) against 96 % with the full device list.
- And RAG inside the *system* prompt is a latency trap: the prompt changes on every request, so the LLM's **prompt cache is discarded**. At ~46 tokens/s of prompt processing that costs ~25 s per request.
- With tens to ~100 exposed devices, a **fixed compact list** (stable prefix, cache always valid) beats retrieval. RAG would pay off with several hundred devices or a much larger context.

## 3. Compact prompt and proxy

Described in [02](02-architecture.md). This was the **biggest single gain**, bigger than any change of model: prompt ÷ 2.3, one tool turn, validated tool names, forced decoding settings, a stable cache.

## 4. Deterministic guard-rails

Three small pieces of code fix three failure modes more reliably than more training: invented values on unavailable sensors, spurious refusals after a successful tool call, and unsupported numbers in web answers ([02](02-architecture.md)).

## 5. Private web search

A `web_search` tool executed by the proxy against a local SearXNG instance. Design choices:

- Queries are **anonymized** (device, room and alias names removed, except weather/generic words) and logged for **7 days** only.
- Snippets are cut to 4 results x 230 characters; shorter snippets were faster (−3 s) but noticeably less accurate.
- An **in-memory** cache (10 min, 100 entries, never written to disk) avoids repeating identical searches.
- Public search engines rate-limit bursts (HTTP 429): training data for this tool is therefore mostly **synthetic** (snippets fabricated in the style of real ones, answers computed by rule, real snippets from other queries used as distractors).

## 6. Other models

- **CroissantLLM 1.3B** (French-centric Llama architecture, 2,048-token context): trained with the same recipe. The first version scored 37 % because it was trained with a different **tokenizer** (HF) than the one used at inference (llama.cpp): the JSON key `arguments` became `a`. Retraining with llama.cpp's tokenization fixed it.
- **Qwen3-0.6B**: same data and recipe as the 1.7B, to measure the speed/quality trade-off.

## How the benchmark works

- **92 French phrases** (data/benchmark_fr_92.json): lights, shutters, climate, scripts, lists, information, general knowledge, **traps** (non-existent devices), **noisy transcriptions**, and **adversarial** cases (sensors that are unavailable).
- **Benches**: first tool call; exact framework request + simulated tool results (success or forced error) to detect loops and false confirmations; compact pipeline; web routing and accuracy; stress replays.
- **Safe testing**: a *simulation proxy* strips every tool call, and a separate agent attached to no pipeline lets the exact framework request be replayed **without executing anything**.
